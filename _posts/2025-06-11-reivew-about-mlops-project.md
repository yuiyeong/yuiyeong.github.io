## 📝  우리가 프로젝트로 배운 것
프로젝트를 시작하며 우리 팀은 명확한 학습목표를 설정했다.

**_선택과 집중을 통한 MLOps 핵심 역량 습득_**

**_Airflow 중심의 ML Pipeline 구축 경험_**

**_팀 협업을 통한 실무형 프로젝트 진행_**

MLOps의 방대한 영역에서 길을 잃지 않기 위해, **Apache Airflow**를 중심으로 한 ML 파이프라인 구축에 집중하기로 결정했다.

## 🎯 내가 한 행동의 결과로 어떤 지점을 달성하고, 어떠한 깨달음을 얻었는가?

팀장이다 보니 혼자하기 보다는 함께 할 수 있는 방향으로 최대한 이끄려고 했다.
사실 개인적인 성향이 강한 나였기에, 이러한 방향으로 가는 것은 나에게 매우 큰 도전이었다.
하지만, 역시 팀의 결속이 강해지니까 프로젝트 전보다는 훨씬 성공적으로 마무리되었다고 생각한다.

기술적으로는 데이터 수집부터 모델 서빙까지 완전한 end-to-end MLOps 파이프라인을 구축했다. Postgres, Airflow, FastAPI가 통합된 안정적인 컨테이너 환경을 구성했으며, Weights & Biases를 통한 모델 실험 버전 관리 시스템도 구현했다.

협업 측면에서는 우리 팀이 정한 체계적인 일정 관리가 효과적이었다. 05.26 프로젝트 셋업부터 06.10 최종 발표까지 각 단계별 목표를 명확히 설정하고 달성해나갔다. 특히 Docker 환경 구축, 실시간 데이터 수집 파이프라인, 자동화된 워크플로우, 다양한 ML 모델 비교, RESTful API 엔드포인트까지 모든 목표를 성공적으로 완료했다.

핵심 깨달음은 **"MLOps는 기술의 조합이 아닌 전체 시스템의 설계"** 라는 점이었다.
개별 도구의 사용법보다 전체 파이프라인에서 각 컴포넌트가 어떻게 연결되고 상호작용하는지가 더 중요했다.

## 🧐 새로운 시도와 그에 따른 득실

전 프로젝트와 다르게 이번 프로젝트는 **모두가, 모든 프로세스를 경험해보자** 역시 목표였기에, 아래와 같이 스케쥴을 잡고 마지막날에는 오프라인으로 모여서 "무조건" 그 기능을 구현하기로 계획했다.

| 기간            | Task                                              |
| ------------- | ------------------------------------------------- |
| 05.26 - 05.26 | • 프로젝트 셋업                                         |
| 05.27 - 05.29 | • 기상청 API 연동 • 데이터 수집 스크립트 • Ncloud Storage 연동    |
| 05.30 - 05.31 | • Airflow 설정 및 구성 • 데이터 파이프라인 DAG 구현 • 파이프라인 모니터링 |
| 06.01 - 06.03 | • 모델 설계 및 구현 • Weights & Biases 연동 • 모델 평가 및 검증   |
| 06.04 - 06.05 | • FastAPI 서비스 개발 • 모델 서빙 로직 • API 문서화 및 테스트       |
| 06.06 - 06.09 | • CI/CD • 프로젝트 산출물 제출                             |
| 06.10 - 06.10 | • 최종 발표                                           |

이러한 변화는 여러 긍정적 효과를 가져왔다. 오프라인 모임을 통해 확실한 진전을 이룰 수 있었고, 모든 팀원이 MLOps의 전체 영역을 경험하여 학습 효과가 극대화되었다. 실시간 통합으로 에러를 빠르게 발견하고 해결할 수 있어 문제 해결 속도도 향상되었다.

하지만 **오프라인 모임의 빈도**가 높아 후반부로 갈수록 팀원들의 피로도가 누적되는 부작용도 있었다. 거리가 모두 멀었던 탓에 잦은 오프라인 모임이 부담으로 작용하기도 했다.

## 🚧 마주한 한계와 아쉬운 점

가장 큰 한계는 10일이라는 짧은 기간에 Airflow, Docker, 클라우드 인프라를 모두 다루기에는 각 도구의 러닝 커브가 너무 가파르다는 점이었다.

개인적으로는 **MLOps를 지금 이 시기에 학습하는 것**에 대한 회의감이 있었다. MLOps는 CS 지식, 인프라 경험, DevOps 역량, 그리고 ML 실무 경험이 모두 갖춰진 후에 다뤄야 하는 고급 영역이라고 생각했기 때문이다. 이러한 의문이 초기 학습 동기에 영향을 미쳐 속도가 나지 않았던 점이 아쉬웠다. 하지만 프로젝트를 진행하면서 "전체적인 흐름을 이해하고 관련 도구를 한번이라도 사용해본다"는 것의 가치를 인정하게 되었다.

## 🔮 다음번엔...

다음 대회는 **Image Classification 대회**이며, Upstage에서 제공하는 클라우드 인스턴스를 활용할 예정이다. 이번 프로젝트에서 학습한 Weights & Biases를 활용하여 팀원 간 실험 결과 공유 시스템을 구축할 계획이다. 모델 버전 관리와 성능 비교를 위한 경량화된 MLflow 파이프라인을 구성하고, 하이퍼파라미터 튜닝과 모델 비교를 자동화하는 Airflow 기반 워크플로우를 설계해보고 싶다.

## 🏁 결론

이번 MLOps 프로젝트는 **기술적 도전과 협업의 가치**를 동시에 경험할 수 있는 의미 있는 시간이었다.
비록 각 도구의 깊이 있는 이해에는 한계가 있었지만, **전체 ML 파이프라인이 어떻게 구성되고 운영되는지**에 대한 전체적인 그림을 그릴 수 있게 되었다.

특히 팀장으로서 기술적 의사결정과 팀 관리를 동시에 경험한 것은 향후 실무에서 큰 자산이 될 것이다.
**MLOps의 본질은 도구의 사용법이 아닌 시스템 사고**라는 깨달음을 얻었으며, 이는 향후 어떤 기술 스택을 다루든 적용할 수 있는 중요한 인사이트가 될 것이다.
